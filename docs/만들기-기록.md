# 만들기 기록 — 비개발자가 AI와 함께 서비스 만들기

이 파일은 "온라인 항구" 서비스를 만드는 과정을 단계마다 짧게 적어두는 일지입니다.
나중에 강의 자료로 쓸 수 있도록, 매 단계에 **무엇을 했는지 / 왜 그렇게 했는지 / 배운 점**을 남깁니다.

---

## 0단계. 기획 정리와 세팅 방향 잡기 (2026-11-15)

**무엇을 했나**
- 소밍이 서비스의 이유(Why), 구조(세 개의 방), 방 1의 흐름, 분위기, 지켜야 할 원칙을 글로 정리해 AI에게 전달했다.
- AI는 코드를 바로 짜지 않고, 필요한 도구·준비물·작업 단계를 먼저 제안했다.
- 이 기록 파일을 만들었다.

**왜 이렇게 했나**
- 집을 짓기 전에 설계도와 자재 목록을 먼저 확인하는 것과 같다. 방향을 먼저 맞추면 나중에 다시 짓는 일이 줄어든다.

**AI가 제안한 구조 (아직 확정 전, 소밍의 확인 대기 중)**
- 화면(사이트 본체): Next.js — 방을 나중에 쉽게 붙일 수 있는 집 뼈대
- 저장소 겸 관리 화면: Supabase — 엑셀 표처럼 생긴 화면에서 장소·질문·문장을 직접 수정
- 인터넷에 공개: Vercel — 만든 집에 주소를 달아주는 곳
- 코드 보관: GitHub — 변경 이력이 모두 남는 작업 금고
- 내 컴퓨터 설치: 없음 (작업은 클라우드에서 진행)

**작업 단계 초안**
1. 뼈대 세우기: 세 개의 방 구조 + 첫 화면
2. 방 1 화면 흐름 6장면 (가짜 데이터로)
3. 저장소 연결 + 소밍이 내용을 직접 바꾸는 관리 방법
4. 문장 나누기·건네받기·"함께해요" + 안전장치
5. "지금 ○명이 함께" + 수면 위 빛
6. 인터넷에 공개 + 휴대폰 점검
7. (나중에) 방 2, 방 3

**강의용 메모**
- 좋은 첫 요청의 구성: 이유 → 구조 → 세부 흐름 → 분위기 → 지켜야 할 것 → 일하는 방식.
- "바로 코드 짜지 말고 먼저 안내해줘"라고 말한 것이 핵심. AI에게도 일하는 순서를 정해줄 수 있다.

**다음에 정할 것**
- 제안된 도구 구조에 동의하는지
- 소밍레터를 이미 운영 중인지 (어떤 서비스로?)
- 건네받는 문장을 소밍이 미리 읽고 승인하는 방식으로 할지

## 0-2단계. "방 4. 무대" 추가에 따른 설계 재점검 (2026-11-15)

**무엇을 했나**
- 소밍이 네 번째 방 "무대"(호스트의 이야기 / 나의 이야기 노트 / 모두의 무대)를 구상해 전달했다.
- 코드는 짜지 않고, 이 기능이 기존 설계에 주는 영향만 AI와 함께 점검했다.

**왜 이렇게 했나**
- 무대는 방 1 이후에 만들지만, "내 문장이 내 노트에 쌓인다"는 부분은 방 1의 저장 방식에 영향을 준다.
  집을 다 지은 뒤 배관을 새로 까는 것보다, 지을 때 배관 자리를 미리 내두는 편이 쉽다.

**구조가 바뀌는 점 (AI 제안, 소밍 확인 대기 중)**
- 방이 3개에서 4개로 늘어난다.
- 방 1의 문장을 "익명 번호표"와 묶어서 저장한다 (이름·이메일은 여전히 받지 않음).
- 기록을 이어가는 방법: 기본은 브라우저 번호표, 원하는 사람만 "나만의 열쇠 문구"를 받아두는 방식을 추천.
- 모든 나눔 글(문장, 이야기, 반응)에 "대기 / 승인 / 가림" 상태를 두어 하나의 관리 방식으로 통일한다.
- 방 1 마지막 화면에 "이번 주 소밍의 이야기" 자리를 미리 비워둔다.

**순서 변경**
- 전체 순서는 그대로. 다만 3단계(저장소 설계) 때 번호표·노트·삭제 기능의 자리를 미리 잡는다.
- 무대 안에서는 호스트의 이야기 → 나의 이야기 노트 → 모두의 무대 순서를 추천.

**강의용 메모**
- 나중에 만들 기능이라도 미리 말해두면, 지금 만드는 부분의 설계가 달라질 수 있다.
- 기능을 더할 때는 "이게 기존 약속(완전 익명, 최소한의 글자)과 부딪히지 않나?"를 함께 점검한다.

**아직 답이 필요한 것**
- 0단계의 질문 4개 (도구 구조, 매일 승인 방식, 소밍레터, 가져갈 한 가지 느낌)
- 기록 이어가기 방식, 반응 공개 범위, 마지막 화면의 링크 개수

## 0-3단계. "모두의 무대" 구체화 (2026-11-15)

**무엇을 했나**
- 소밍이 모두의 무대를 다시 정의했다: 얼굴 없이 자기 이야기로 주인공이 되는 곳.
  승인된 이야기는 하루에 하나, 방 1에서 "오늘의 이야기"로 바다와 함께 보여지고,
  반응은 며칠 뒤 편지처럼 한 번에 전달된다.
- 여전히 코드는 짜지 않고, 설계와 안내 문구 초안만 만들었다.

**AI가 제안한 것 (소밍 확인 대기 중)**
- 편지 받는 방법: 이야기를 올릴 때 "열쇠 문구"와 "편지 도착 날짜"를 함께 건넨다.
  알림 없이도 그 날짜에 항구로 돌아오면 노트 안 편지함에 편지가 와 있다.
- "오늘의 이야기"는 방 1의 필수 장면이 아니라, 원하는 사람만 여는 문으로 둔다 (5분 약속 지키기).
- 긴 이야기는 "먼저 나만 간직 → 원하면 무대에" 두 걸음으로 나눈다.
- 무대에 오르지 못한 이야기에도 "거절" 대신 소밍의 한마디가 가도록 한다.
- 반응이 하나도 없는 편지가 생기지 않게, 소밍의 반응 하나를 항상 넣는다.
- 음성 올리기는 글이 자리 잡은 뒤에 여는 것을 추천 (목소리는 알아볼 수 있고, 확인에 시간이 든다).

**강의용 메모**
- 기능을 설명할 때 "왜"를 먼저 말하면(누구나 주인공이 되고 싶지만 앞에 서기는 불편하다),
  AI가 기능 목록에 없던 빈틈(거절당한 사람의 마음, 빈 편지함)까지 함께 찾아줄 수 있다.
- 화면의 문구도 설계의 일부다. 버튼 하나의 말투가 서비스의 태도를 정한다.

**아직 답이 필요한 것**
- 이전 질문들 + "오늘의 이야기" 위치, 이야기가 없는 날 처리, 음성 시작 시점

## 0-4단계. 결정: 사전 승인 없이 바로 올라가게 (2026-11-15)

**무엇을 결정했나**
- 문장·이야기·반응 모두 소밍의 사전 승인 없이 바로 전달된다.
- 이유: 승인할 것이 너무 많아져 혼자 운영하기 어렵다.

**대신 안전을 맡는 장치 (AI 제안)**
- 자동 거름망: 욕설, 연락처, 링크, 광고는 저장 전에 걸러진다.
- 위기 표현 감지: 해당 글은 건네지 않고, 쓴 사람에게 상담 안내를 보여준다.
- "가리기" 버튼: 받은 사람이 바로 숨길 수 있고, 여러 번 가려진 글은 자동으로 내려간다.
- 소밍은 관리 화면에서 언제든 글을 내릴 수 있다 (의무가 아니라 선택).

**강의용 메모**
- 설계는 "이상적인 안전"과 "혼자 운영할 수 있는가" 사이의 균형이다.
  운영자가 지치면 서비스가 멈추므로, 지속 가능한 쪽을 고르는 것도 좋은 설계 판단이다.
- AI의 추천을 그대로 따르지 않고 자기 상황에 맞게 바꾸는 것이 만드는 사람의 역할이다.

**추가 결정: 마지막 화면의 중심**
- 소밍의 답: 마지막 화면에서 가장 중요한 것은 "각자 자기다움을 찾고 가는 것".
- AI 제안: 마지막 화면의 주인공을 링크가 아니라 "오늘 내가 남긴 문장"으로 한다.
  다른 방으로 가는 링크는 아주 작게, 또는 메뉴 안으로 옮긴다.
- 강의용 메모: "무엇을 넣을까"보다 "무엇을 느끼고 가게 할까"를 먼저 정하면 화면에 넣을 것이 저절로 줄어든다.

## 1단계. 뼈대 세우기 (2026-11-15)

**시작 전에 바뀐 방향**
- 첫 화면은 "소밍이 지금 있는 곳"이 아니라, 사람들이 가보고 싶었지만 가보지 못한 **세계의 좋은 곳들**을 매일 한 곳씩 보여준다 ("오늘의 항구").
- 따라서 배경 영상/사진은 소밍이 직접 찍은 것만이 아니라, 무료로 쓸 수 있는 자연 영상도 함께 쓰게 된다 (사용 조건은 넣기 전에 확인).

**무엇을 했나**
- Next.js로 사이트의 뼈대를 세웠다 (집의 골조).
- 네 개의 방으로 가는 길을 만들었다: 오늘의 쉼(`/`), 다음 항구(`/next-harbor`), 항구 열기(`/open-harbor`), 무대(`/stage`). 방 1 외에는 "준비 중인 방" 화면만 있다.
- 방 1의 첫 화면을 만들었다: 오늘의 항구(나라, 장소, 한 줄 소개), "지금 ○명이 함께 쉬고 있어요", "쉬러 들어가기" 버튼, 수면 위 작은 빛.
- 휴대폰 크기 화면으로 열어 확인하고 `docs/화면/`에 사진을 남겼다.

**아직 가짜인 것 (솔직한 목록)**
- 배경: 실제 영상이 아니라 색으로 그린 임시 배경.
- 장소 7곳: AI가 넣은 예시. `content/places.ts`에 있다.
- "7명": 고정된 임시 숫자.
- "쉬러 들어가기": 눌러도 아직 아무 일도 일어나지 않는다 (2단계에서 연결).

**만난 문제와 해결**
- 최신 Next.js는 화면을 미리 만들어두려 해서, "오늘 날짜에 따라 바뀌는 내용"을 그대로 쓰면 조립이 실패했다.
  → 날짜가 필요한 부분만 "방문한 순간에 그리기"로 표시해 해결했다.
- 강의용 메모: AI도 새 버전 도구에서는 틀릴 수 있다. 도구에 들어 있는 설명서를 찾아 읽고 고쳤다. 오류는 실패가 아니라 과정의 일부다.

**다음 단계**
- 2단계: 방 1의 여섯 장면(들어오기 → 몸 열기 → 숨 고르기 → 한 문장 → 건네받기 → 다시 일상으로)을 가짜 데이터로 이어 붙이기.

**아직 답이 필요한 것**
- "무대에서 내 이야기를 하는 거야, 다른 사람이 아니라"의 뜻 확인.
- 오늘의 항구가 바뀌는 주기 (매일 / 매주).

## 1-2단계. 두 언어, 글꼴, 실사 배경 준비 (2026-11-15)

**소밍의 결정**
- 무대: 누구나 설 수 있고, 모두 자기 자신의 이야기를 한다.
- 오늘의 항구: 매일 바뀐다.
- 첫 화면의 분위기와 문구: 좋다.
- 새 요청 세 가지: 배경을 실사처럼 / 글꼴은 Pretendard / 한국어·영어 버전.

**무엇을 했나**
- 한국어·영어 버전: 주소가 `/ko`, `/en`으로 나뉜다. 주소 없이 들어오면 브라우저 언어를 보고 한국어 사용자는 `/ko`, 그 외는 `/en`으로 안내한다. 화면 오른쪽 위에 작은 언어 바꾸기가 있다.
  - 화면 문구는 `content/i18n.ts`, 장소는 `content/places.ts`, 방 이름은 `content/rooms.ts`에 두 언어로 나란히 적는다.
- Pretendard 글꼴을 사이트 안에 넣었다 (무료 공개 글꼴, 외부 서버에 의존하지 않음).
- 실사 배경을 넣을 자리를 만들었다: `public/places/`에 사진을 넣고 `content/places.ts`에 파일 이름을 적으면, 화면 가득 사진이 아주 천천히 움직인다. 사진이 없는 장소는 임시 색 배경이 나온다.
- 화면 사진: `docs/화면/1단계-첫화면-ko.png`, `docs/화면/1단계-첫화면-en.png`

**하지 못한 것 (솔직한 기록)**
- 실제 사진은 아직 넣지 못했다. 작업실이 허락된 사이트에만 접속할 수 있어서, 소밍의 승인을 받아 위키미디어 공용 접속을 열었다. 검색은 되었지만 사진 내려받기는 그 사이트의 접속 제한(너무 많은 요청)에 걸렸다.
- 사이트가 일부러 막아둔 것을 억지로 넘지 않고 멈췄다. 사진은 소밍이 직접 골라 전달하는 방식으로 진행한다.

**강의용 메모**
- 권한 요청의 좋은 예: "무엇을, 왜, 무엇이 가능해지는지"를 먼저 듣고 승인했다.
- AI가 막혔을 때 억지로 돌아가지 않고 멈춰서 알리는 것이 맞다. 사진처럼 "취향"이 담기는 재료는 만드는 사람이 직접 고르는 편이 결과도 더 좋다.
- 두 언어를 지원하면 나눔 문장도 두 언어로 들어온다. 4단계에서 "같은 언어로 남긴 문장끼리 건네기"를 정해야 한다.

**다음 단계**
- 사진 받기 → 실사 배경 적용
- 2단계: 방 1의 여섯 장면
